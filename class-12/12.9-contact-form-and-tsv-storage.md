# 12.9 Contact Form + TSV Storage

This is the final tutorial for Class 12.

We’ll focus on the **Contact Us** form and how we persist submissions to a **TSV file** (tab-separated values).

The form and validation patterns are primarily based on our work last week:

- a field spec array
- input retrieval with `filter_input()`
- server-side validation
- sticky form values + field-level errors
- PRG (Post-Redirect-Get) after successful submission

## Where the Contact Form Lives

The Contact Us page is a PHP page template:

- `class-12/starter-files/app/views/pages/contact-us.php`

It is routed by the front controller when:

- `page=contact-us`

and (with Apache rewriting) that means:

- `/contact-us`

## The Field Spec (One Source of Truth)

The contact form fields are defined in:

- `class-12/starter-files/app/lib/fields.php` (`contactFields()`)

That spec defines:

- `label`
- `type` (text/email/textarea)
- `default`
- `sanitize` filter (ex: `FILTER_SANITIZE_EMAIL`)
- `rules` (required, minLength, maxLength, email)
- HTML attributes for UX (required, minlength, maxlength, autocomplete)

Because we render from the spec, adding/removing a field is mostly:

- update `contactFields()`
- ensure storage writes the new column

## The POST Flow (Read → Validate → Save → Redirect)

The contact page follows the familiar server-side form flow:

1. Initialize `$values` and `$errors`
2. On POST:
   - `readValues($fields)`
   - `validateValues($fields, $values)`
3. If valid:
   - save the submission to storage
   - redirect to a GET page with `success=1` (PRG)
4. Render the form (sticky values + errors) or show the success banner

You can see the redirect here:

- `header('Location: ' . constructUrl('contact-us', ['success' => '1']), true, 303);`

That means refreshing the page does not re-submit the POST.

## Rendering Sticky Fields + Errors

The page uses:

- `renderField(...)` from `class-12/starter-files/app/lib/render.php`

That rendering helper uses:

- `$values` for sticky form values
- `$errors` for per-field messages
- escaping (so untrusted values are safe in HTML)

## TSV Storage: What It Is

TSV is “tab-separated values”.

It’s like CSV, but the separator is a tab character:

- column1 `\t` column2 `\t` column3

Why TSV can be nice:

- easy to append a new record (one line)
- easy to open in spreadsheet tools
- simple enough for small projects and demos

## Where TSV Data Is Stored

The TSV file path is defined in:

- `class-12/starter-files/app/lib/storage.php` (`dataFilePath()`)

It writes to:

- `app/storage/contacts.tsv`

This is intentionally outside `public/`:

- users should not be able to request the TSV file directly via a URL

## Creating the TSV File (Header Row)

Before saving the first submission, the app ensures the file exists:

- `ensureDataFileExists()`

If the file does not exist, it creates it and writes a header row.

The header row is derived from the field spec:

- column names = `array_keys(contactFields())`

This is a key maintainability benefit:

- your storage columns stay aligned with the spec

## Writing a Submission (Appending a Row)

Saving a submission is handled by:

- `saveData($values)` in `class-12/starter-files/app/lib/storage.php`

It writes columns in the same order as the spec.

Important detail:

- it replaces any `\t` characters in submitted values with spaces before writing
  (so one field cannot “break” the TSV column structure)

## Notes and Limitations (Important)

TSV is great for learning and small demos, but it has limitations:

- concurrent writes can be tricky (file locking becomes important)
- it’s not a relational database
- editing/deleting specific records is not as natural as in a database

In real applications you typically move to:

- a database (MySQL/Postgres/SQLite), or
- a more structured store (JSON with IDs, plus proper locking), depending on needs

For this week, TSV is a clean way to practice:

- validated form submission handling
- file-based persistence

# 12.2 Apache `.htaccess` Rewriting Basics

In 12.1 we introduced Composer and autoloading.

This tutorial covers a common “real server” topic: using Apache `.htaccess` files to enable **clean URLs**
and route requests through a **front controller** (usually `public/index.php`).

Apache is the most widely used web server, and `.htaccess` is a common way to configure it in shared hosting
environments.

## What `.htaccess` Is (High Level)

Apache allows per-directory configuration via a file named:

- `.htaccess`

This is useful in shared hosting environments where you cannot edit the main Apache config.

Important:

- `.htaccess` only works if Apache is configured to allow it (via `AllowOverride`).

## Clean URLs and the Front Controller Pattern

Without rewriting, a PHP site often uses URLs like what we saw in chapter 13:

- `/index.php?page=contact-us`

With rewriting, we can use cleaner URLs like:

- `/contact-us`

But PHP still needs a single entry point so it can:

- bootstrap the application (autoload, config, helpers)
- decide which page to serve
- handle “not found” cases consistently

That entry point is the **front controller**:

- `public/index.php`

## Enabling `mod_rewrite`

Apache URL rewriting uses the rewrite engine:

- `mod_rewrite`

On systems where you control the server, `mod_rewrite` must be enabled for rewrite rules to work.
(On many shared hosts it is already enabled.)

## The Core Directives

The `.htaccess` rewrite rules you’ll see most often look like this:

```apacheconf
RewriteEngine On

RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^(.*)$ index.php?page=$1 [L,QSA]
```

This exact pattern is in:

- `class-12/starter-files/public/.htaccess`

Let’s break it down.

### `RewriteEngine On`

Turns rewriting on for this directory.

### `RewriteCond %{REQUEST_FILENAME} !-f` and `!-d`

These two conditions say:

- Only rewrite if the request is NOT an existing file
- and NOT an existing directory

That matters because we *do not* want to rewrite requests for real assets like:

- `/favicon.ico`
- `/assets/app.css`

### `RewriteRule ^(.*)$ index.php?page=$1 [L,QSA]`

This says:

- For any path (capture it as `$1`)
- route the request to `index.php`
- and pass the captured path as a query parameter named `page`

So:

- `/contact-us` becomes internally: `index.php?page=contact-us`

Flags:

- `[L]` means “last rule” (stop processing rewrite rules if this matches)
- `[QSA]` means “query string append”
  - if the URL already has query parameters, keep them
  - example: `/portfolio?sort=asc` becomes `index.php?page=portfolio&sort=asc`

## Internal Rewrite vs Redirect

The rule above is an **internal rewrite**:

- the browser address bar stays `/contact-us`
- Apache serves the response by running `index.php`

A **redirect** sends a 301/302 response to the browser and changes the URL in the address bar.

Redirects are commonly used for:

- forcing HTTPS
- forcing `www` vs non-`www`
- removing trailing slashes (or adding them consistently)

## Common Rewrite Gotchas

### 1) The Rewrite Base / Subdirectories

If your site is served from a subdirectory (not the domain root), you sometimes need `RewriteBase`.

In many simple class projects, you can avoid this by ensuring:

- Apache’s document root points at the project’s `public/` directory

### 2) Infinite Rewrite Loops

If you rewrite everything to `index.php` but forget to exclude existing files/directories, you can break asset
requests or accidentally rewrite requests you didn’t intend.

The `!-f` and `!-d` conditions prevent this in our starter.

### 3) Security: Don’t Use the Raw Path Unfiltered

When you rewrite a path into `page=...`, the value is user-controlled input.

You still must:

- sanitize/normalize it
- map it only to allowed pages
- avoid directory traversal / file inclusion vulnerabilities

You can see an example approach in:

- `class-12/starter-files/public/index.php`

## Testing

Apache `.htaccess` is not used by PHP’s built-in dev server (`php -S ...`).

To test rewriting rules, you need an Apache environment (local Apache, XAMPP/WAMP/MAMP, a VM, or hosting)
that:

- serves your app from `public/`
- has `mod_rewrite` enabled
- allows `.htaccess` overrides

We have Apache installed already and configured to use port 8080 to serve the `public/` directory just as we did
with the PHP dev server, so we just need to make sure that the PHP dev server isn't running and then start Apache.
We do that by running:

```bash
sudo service apache2 start
```

# 11.10 Wrap-Up and Common Pitfalls

This week (Chapter 12) was about validating form data and building user-friendly, secure form flows.

We also expanded beyond the book by discussing:

- sanitization filters available via `filter_input()`
- HTML5 browser validation and attributes
- JavaScript validation as progressive enhancement

Now we’ll wrap up with a checklist and a set of common pitfalls that show up constantly in real PHP apps.

## Core Checklist (What You Should Be Able to Explain)

- Why client input is untrusted (the trust boundary)
- Validation vs sanitization vs escaping
- Why server-side validation is required even when HTML5/JS validation exists
- How sticky forms and field-level error messages improve UX
- Why PRG (303 redirect after POST) prevents duplicate submissions
- How `filter_input()` return values work (`null` vs `false` vs “a value”)

## Common Pitfalls

### 1) Confusing Sanitization with Validation

- `FILTER_SANITIZE_EMAIL` cleans input.
- It does not guarantee a valid email address.

Best practice:

- sanitize, then validate with `FILTER_VALIDATE_EMAIL`.

### 2) Forgetting Output Escaping (XSS)

Even validated input must be escaped when rendered into HTML:

```php
<?php
print h($value);
```

If you ever print raw user input into a page, you risk XSS.

### 3) Double Escaping

If you escape on input and escape again on output, your page shows `&amp;lt;` instead of `<`.

Best practice:

- store raw (possibly trimmed/sanitized) strings
- escape on output only

### 4) Missing Checkbox Keys

Unchecked checkboxes are often missing from request data.

Best practice:

- normalize to boolean:
  - present => `true`
  - missing => `false`

Then validate with a rule like `requiredTrue` when needed.

### 5) The “0 Is Valid” Validation Gotcha

`FILTER_VALIDATE_INT` returns:

- an integer (including 0) when valid
- `false` when invalid

So never do:

- `if (!$value) ...`

Instead:

```php
<?php
if ($value === false) {
    // invalid
}
```

### 6) Not Validating Allowed Values for Select/Radio

Never assume a select/radio submission is one of the options you rendered.

Best practice:

- validate against an allowlist (rule like `in`)

### 7) Repeating Rules in Many Places

If “requestedAmount must be between 100 and 5000” appears:

- in HTML attributes
- in PHP retrieval
- in validation

…it will eventually drift out of sync.

Best practice:

- keep rules in one source of truth (field spec) and generate everything else.

### 8) Processing a POST and Rendering HTML Without Redirecting

If you output the success page directly after POST:

- refresh can re-submit the POST

Best practice:

- PRG with a 303 redirect after successful save.

### 9) Not Handling File Writes Safely

When persisting to JSON:

- a request can die mid-write
- concurrent writes can overlap

Best practice for this class:

- write to a temp file with `LOCK_EX`
- `rename()` into place (atomic write)

# 11.1 Validation Mindset

Chapter 12 is about validating form data. This is one of the biggest steps from “PHP scripts” to “real web apps”.

When you accept user input, you’re doing two things at the same time:

- building a good user experience (helpful errors, less frustration)
- protecting the application and its data (security and integrity)

## The Trust Boundary

In a web app, the trust boundary is simple:

- **Anything that comes from the client is untrusted.**

“The client” includes:

- HTML forms
- query strings
- cookies
- headers
- JavaScript code running in the browser

Even if you wrote the frontend, the browser can be modified, requests can be crafted manually, and attackers can
send requests without using your form at all.

That is why **server-side validation is required**.

## Validation vs Sanitization vs Escaping

These terms get mixed up a lot. Here’s the mental model we will use all term:

### Validation

Validation answers:

- “Is this value acceptable for our rules?”

Examples:

- required fields are not empty
- email is in a valid format
- number is within a specific range
- select/radio value is one of a known set of allowed values

Validation usually produces:

- a *validated value* (often normalized) and/or
- an *error message* describing what is wrong

### Sanitization (Normalization)

Sanitization answers:

- “Can we safely clean/normalize this value into a predictable shape?”

Examples:

- trim leading/trailing whitespace
- sanitize an email value so it removes illegal characters
- strip tags from text fields when you do not want markup

Sanitization is not a substitute for validation.

For example, sanitizing an email doesn’t guarantee it is a valid email address.

### Escaping (Output Safety)

Escaping answers:

- “How do we safely display this value in HTML without executing it as markup or JavaScript?”

For HTML, the most common tool is:

```php
<?php
htmlspecialchars($value, ENT_QUOTES, 'UTF-8');
```

In other words:

- **Validate + sanitize on input.**
- **Escape on output.**

## Client-Side Validation: UX, Not Security

Client-side validation can be useful because it’s fast and friendly:

- instant feedback while typing
- fewer round trips to the server
- better mobile keyboards for certain input types (email, url, number)

But client-side validation can be bypassed:

- disable JavaScript
- change HTML attributes in DevTools
- send requests directly (curl, Postman, scripts)

So our rule is:

- **Never rely only on client-side validation.**
- Use it to improve UX, but always validate again on the server.

## What We’re Building This Week

We’re going to build a small “form generation + validation framework” and use it to implement a
**Grant Application** form.

The key idea is “one source of truth”:

- we define fields and rules in a configuration array
- we use that same configuration to:
  - render HTML inputs
  - display errors
  - retrieve data with `filter_input()`
  - validate values consistently

This keeps form code from turning into copy/paste chaos as a project grows.

## What “Good” Validation Looks Like

We want a consistent pattern:

1. Start with defaults (empty values and no errors).
2. On POST:
   - retrieve values (prefer `filter_input()` / `filter_input_array()`)
   - sanitize/normalize into predictable shapes
   - validate each field and collect per-field errors
3. If there are errors:
   - re-render the form (sticky values + field-level error messages)
4. If it is valid:
   - save to JSON
   - redirect (PRG)
   - show a success message on the GET page

## A Tiny Preview (Errors + Sticky Values)

We’ll build this properly later in the week, but here’s the basic shape you should expect:

```php
<?php
$values = [
    'applicantName' => '',
    'contactEmail' => '',
];

$errors = [
    'applicantName' => '',
    'contactEmail' => '',
];

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    // retrieve + sanitize
    // validate into $errors

    $hasErrors = false;
    foreach ($errors as $message) {
        if ($message !== '') {
            $hasErrors = true;
            break;
        }
    }

    if (!$hasErrors) {
        // save + PRG redirect
    }
}
```

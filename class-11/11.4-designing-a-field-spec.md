# 11.4 Designing a Field Spec (One Source of Truth)

In 11.1–11.3 we covered the “why” of validation and the tools available:

- server-side validation is required
- `filter_input()` helps retrieve and sanitize/validate request values
- HTML5 attributes improve UX, but are not a security boundary

Now we start building our form generation + validation framework.

The first step is deciding what our “source of truth” looks like.

## The Problem We’re Solving

If you build forms by hand, you quickly end up duplicating the same information in multiple places:

- the form HTML (label, required markers, min/max)
- the request retrieval logic (`filter_input()`)
- the server-side validation rules and messages
- sticky values + error display rules

Duplicated rules inevitably drift out of sync.

So we’ll create a **field spec** array that describes:

- what fields exist
- how to render them
- how to retrieve them
- how to validate them

## A Field Spec: What We Want It to Include

For each field, we want to capture:

- `name` (the key in the request, e.g. `contactEmail`)
- `label` (human-friendly label)
- `type` (text/email/textarea/select/radio/checkbox/number/date/url)
- `default` (sticky default value)
- server-side rules (required, min/max, allowed values, regex, etc.)
- optional sanitization filter (via `filter_input()`)
- HTML attributes for UX (`required`, `minlength`, `pattern`, etc.)
- options for selects/radios (allowed values + labels)

## Recommended Shape (Per Field)

Here is a practical structure we’ll use for the Grant Application form.

We’ll store specs by field name:

```php
<?php
$fields = [
    'applicantName' => [
        'label' => 'Applicant name',
        'type' => 'text',
        'default' => '',
        'sanitize' => [
            'filter' => FILTER_UNSAFE_RAW,
        ],
        'rules' => [
            'required' => true,
            'minLength' => 2,
            'maxLength' => 80,
        ],
        'html' => [
            'required' => true,
            'minlength' => 2,
            'maxlength' => 80,
            'autocomplete' => 'name',
        ],
    ],
];
```

Notes:

- `sanitize` uses the filter API to retrieve/normalize values.
- `rules` are the server-side truth.
- `html` is for UX (often mirrors the rules, but the server-side rules win).

## Example: Email Field (Sanitize + Validate)

```php
<?php
$fields['contactEmail'] = [
    'label' => 'Contact email',
    'type' => 'email',
    'default' => '',
    'sanitize' => [
        'filter' => FILTER_SANITIZE_EMAIL,
    ],
    'rules' => [
        'required' => true,
        'email' => true, // we will validate with FILTER_VALIDATE_EMAIL (or filter_var)
        'maxLength' => 255,
    ],
    'html' => [
        'required' => true,
        'maxlength' => 255,
        'autocomplete' => 'email',
    ],
];
```

Important distinction:

- `FILTER_SANITIZE_EMAIL` is not a guarantee the email is valid.
- We still validate with `FILTER_VALIDATE_EMAIL` as a rule.

## Example: Select / Radio Field (Allowed Values)

For select/radio, we need an allowed list.

```php
<?php
$fields['category'] = [
    'label' => 'Project category',
    'type' => 'select',
    'default' => '',
    'sanitize' => [
        'filter' => FILTER_UNSAFE_RAW,
    ],
    'options' => [
        'education' => 'Education',
        'health' => 'Health',
        'community' => 'Community',
        'environment' => 'Environment',
        'arts' => 'Arts & Culture',
        'technology' => 'Technology',
        'other' => 'Other',
    ],
    'rules' => [
        'required' => true,
        'in' => ['education', 'health', 'community', 'arts', 'technology'],
    ],
    'html' => [
        'required' => true,
    ],
];
```

Why we validate “in list” on the server:

- a client can submit a value that was never in your HTML

## Example: Checkbox Field (Presence)

Checkboxes are special because the key is often missing when unchecked.

We’ll represent a checkbox as a boolean:

```php
<?php
$fields['agreeToTerms'] = [
    'label' => 'I agree to the terms',
    'type' => 'checkbox',
    'default' => false,
    'rules' => [
        'requiredTrue' => true,
    ],
    'html' => [
        'required' => true,
    ],
];
```

This will map to logic like:

- checked => `true`
- unchecked/missing => `false`

## Retrieval: Mapping the Spec to `filter_input()`

We’ll build a function that takes a field spec and returns a “values” array.

Conceptually:

- for a text-like field, call `filter_input()` using the specified sanitization filter
- for a checkbox, treat “present” as true
- for multi-checkbox arrays, use `FILTER_REQUIRE_ARRAY`

The spec makes retrieval consistent and removes repetitive code.

## Why We Keep HTML Attributes in the Spec

HTML5 validation attributes are not security, but they are great UX.

By keeping them in the spec:

- our generated form and our validation rules stay aligned
- we can change a constraint in one place

Remember:

- the server-side rules are the truth
- HTML attributes are a hint and a UX enhancement

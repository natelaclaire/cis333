# 11.7 Sanitization + Normalization + Escaping (Where Each Belongs)

By this point we have three related “input safety” tools on the table:

- sanitization filters (`FILTER_SANITIZE_*`) via `filter_input()`
- normalization steps (trim, type casting, allowed-values mapping)
- output escaping (`htmlspecialchars()` / `h()`)

This tutorial clarifies where each belongs in a real app so you don’t accidentally:

- validate the wrong value
- “sanitize” in a way that breaks user data
- forget output escaping and introduce XSS

## A Practical Pipeline

Here is a good default pipeline for most form fields:

1. **Retrieve** with `filter_input()` (optionally sanitize while retrieving)
2. **Normalize** into a predictable shape (trim, cast, arrays)
3. **Validate** against your server-side rules
4. **Persist** only if valid
5. **Escape on output** every time you render into HTML

This keeps your code understandable and predictable.

## Sanitization: Make the Value Predictable (Not “Safe”)

Sanitization is about shaping input, not declaring it trustworthy.

### Email: sanitize, then validate

```php
<?php
$email = filter_input(INPUT_POST, 'contactEmail', FILTER_SANITIZE_EMAIL);
$email = is_string($email) ? trim($email) : '';

if ($email === '') {
    $error = 'Email is required.';
} elseif (filter_var($email, FILTER_VALIDATE_EMAIL) === false) {
    $error = 'Email must be a valid email address.';
}
```

Why both?

- sanitize removes illegal characters
- validate ensures the result is actually a valid email address

### URL: sanitize, then validate (optional field)

```php
<?php
$url = filter_input(INPUT_POST, 'websiteUrl', FILTER_SANITIZE_URL);
$url = is_string($url) ? trim($url) : '';

if ($url !== '' && filter_var($url, FILTER_VALIDATE_URL) === false) {
    $error = 'Website URL must be a valid URL.';
}
```

### Numbers: sanitize carefully, then validate intent

Sanitizing numbers can be misleading:

- “$1,000” might sanitize to “1000” (which is fine)
- “1e6” might not behave the way you expect depending on your approach

For grant amounts, you usually want business rules:

- whole dollars (integer)
- range limits

That pushes you toward:

- normalize: remove formatting you expect (commas, currency symbol) if you want to support it
- validate: integer and range

## Normalization: Trim, Cast, and Standardize

Normalization makes validation easier and reduces edge cases.

Common normalization steps:

- `trim()` on all text inputs
- cast numeric strings to `int` / `float` only after you know they match the format you expect
- normalize “missing checkbox” to `false`
- ensure arrays are arrays (`[]` when missing)

Example:

```php
<?php
$name = is_string($name) ? trim($name) : '';
```

## “Strip Tags” Is a Business Rule

Some applications allow rich text; others do not.

If your app does **not** allow markup in a text field, you might choose to:

- `strip_tags()` before validation and storage

But treat this as a business decision:

- stripping tags changes the user’s input
- you should do it deliberately, not reflexively

Even if you strip tags, you still must escape on output.

## Escaping: Always on Output (HTML Context)

Escaping is not the same as sanitization.

Even after sanitization + validation, you must escape when rendering into HTML:

```php
<?php
print h($values['projectSummary']);
```

This prevents XSS because the browser will treat `<script>` as text instead of code.

## Avoid “Double Escaping”

A common mistake:

- escaping on input (storing `&lt;` in your JSON)
- escaping again on output (produces `&amp;lt;`)

Avoid this by:

- storing raw strings (possibly trimmed/sanitized)
- escaping only when rendering into HTML

## Allowed Values (Select/Radio): Validation Beats Sanitization

For select and radio inputs:

- sanitization doesn’t solve the real problem
- the real problem is: “Is this one of the allowed values?”

So you validate with an allowed list (`in`):

```php
<?php
if (!in_array($category, $allowedCategories, true)) {
    $error = 'Category must be one of the allowed options.';
}
```

## Checkboxes: Presence Is the Value

Checkboxes are a special case:

- checked => the key exists in the request
- unchecked => the key is missing

So your retrieval layer should normalize to boolean:

- present => `true`
- missing => `false`

Then validate with a `requiredTrue` rule when needed.

## Where This Fits in Our Framework

We will implement sanitization + normalization in two layers:

1. **Retrieval layer** (field spec `sanitize` filter + checkbox/array handling)
2. **Normalization layer** (trim strings, normalize arrays, type casting for validated submissions)

Then the validator runs on normalized values.

# 11.9 JavaScript Validation (Progressive Enhancement)

This chapter is primarily about server-side validation in PHP.

But modern web apps almost always include *some* client-side validation too, because it can dramatically improve
the user experience:

- faster feedback
- fewer server round trips
- clearer “what needs fixing?” moments

The key concept is **progressive enhancement**:

- the app works correctly without JavaScript
- JavaScript adds helpful UX, but does not enforce security

## Why JavaScript Validation Is Not a Security Boundary

Any client-side logic can be bypassed:

- JavaScript can be disabled
- HTML can be edited in DevTools
- requests can be crafted directly

So the rule remains:

- **Server-side validation is always required.**

## What JavaScript Is Good At

JavaScript validation is best used for:

- instant hints (“You need at least 50 characters”)
- formatting help (auto-inserting dashes in a phone number)
- disabling submit until required checkboxes are checked
- showing inline messages before the user submits

Try to avoid:

- complex “business logic” in JavaScript that you don’t also implement on the server

If you do implement a rule in JavaScript, treat it as UX only and always mirror it server-side.

## Two Approaches

### Approach A: Let the Browser Do Most of It

HTML5 already provides:

- `required`, `min`, `max`, `pattern`, etc.

JavaScript can simply improve messaging by calling:

- `checkValidity()`
- `reportValidity()`

Example:

```html
<script>
const form = document.querySelector('form');
form?.addEventListener('submit', (event) => {
  if (!form.checkValidity()) {
    event.preventDefault();
    form.reportValidity();
  }
});
</script>
```

This doesn’t replace server-side validation, but it can make browser feedback more consistent.

### Approach B: Custom Inline Feedback

Example: live character count for a “Project summary” textarea.

```html
<textarea id="projectSummary" name="projectSummary" minlength="50" maxlength="1000" required></textarea>
<div class="form-text"><span id="summaryCount">0</span> / 1000 characters</div>

<script>
const summary = document.querySelector('#projectSummary');
const countEl = document.querySelector('#summaryCount');

function updateCount() {
  const n = summary?.value?.length ?? 0;
  if (countEl) countEl.textContent = String(n);
}

summary?.addEventListener('input', updateCount);
updateCount();
</script>
```

This is a pure UX feature. It doesn’t change the server-side rules.

## Keeping One Source of Truth

Our goal this week is to keep the rules in one place (the field spec + server-side validator).

JavaScript can still be aligned with those rules if we:

- generate `data-*` attributes from the spec (minLength, maxLength, required)
- write JavaScript that reads those attributes

But we should keep that lightweight.

If the JS gets complicated, it becomes a second rules engine, and the rules can drift out of sync.

## Security + UX Summary

- HTML5 attributes and JS validation improve UX.
- They reduce server load and user frustration.
- They can be bypassed.
- Server-side validation remains the source of truth.

# 10.10 Wrap-Up and DevTools Form Inspection

This week (Chapter 11) we built a small server-rendered CRUD application and used it to practice how forms
actually behave in the browser and in PHP.

Before we move on to validation and sticky forms next week (Chapter 12), we want a clear mental model of:

- what the browser sends
- what the PHP server receives
- why PRG matters

## What We Built

We implemented:

- a secure project layout (only `public/` is web-accessible)
- JSON persistence (`app/storage/data.json`)
- course CRUD:
  - create (`/courses/new` + `/courses/create`)
  - list (`/courses`)
  - update (`/courses/edit` + `/courses/update`)
  - delete (`/courses/delete`, POST-only)
- registration create/list/remove:
  - create (`/registrations/new` + `/registrations/create`)
  - list + filter (`/registrations?courseId=...`)
  - remove (`/registrations/delete`, POST-only)

## Chapter 11 Concepts Checklist

Make sure you can explain:

- why GET vs POST matters
- what `method` and `action` do on a `<form>`
- why every input needs a `name`
- why we avoid reading `$_GET`/`$_POST` directly (prefer `filter_input()`)
- why checkboxes are often missing from request data when unchecked
- why everything starts as a string (type casting)
- why we use PRG (303 redirect after POST)
- why we escape output with `htmlspecialchars()` / `h()` (XSS prevention)

## DevTools Walkthrough: What to Look For

Open DevTools -> Network and submit a form (create a course or a registration).

### 1) Confirm the Request Method

Click the request and confirm it is:

- `POST /courses/create` (or similar)

### 2) Inspect the Form Payload

Look for the submitted fields:

- in Chrome, this is typically shown under "Payload" or "Form Data"
- in Firefox, look for the request parameters section

Pay attention to:

- unchecked checkboxes not appearing at all
- multi-checkbox arrays showing repeated keys (or arrays)

### 3) Observe the Redirect (PRG)

After a POST handler runs, our app sends a redirect like:

- `303 See Other` + `Location: /courses?created=1`

In the Network tab you should see:

1. the POST request
2. a redirect response
3. the follow-up GET request

That is PRG in action, and it is why refresh does not re-submit your POST.

# 10.5 Course Delete

Now we add the **Delete** part of CRUD for courses.

In this tutorial we implement:

- a **POST-only** delete handler
- a delete button on the course edit page
- a redirect back to the course list (PRG)
- a discussion about what happens when related data exists (registrations)

## New Route

- `POST /courses/delete`

File:

- `app/pages/courses-delete.php`

## Why Delete Should Not Be a GET

GET requests are meant to be safe to repeat:

- the browser might prefetch them
- crawlers might follow them
- users might refresh them

If we allowed `GET /courses/delete?id=...`, it would be very easy to accidentally delete data.

So we use a form with `method="post"` and a handler that only accepts POST.

## Delete Button (On the Edit Page)

We add a second form to the edit page:

```html
<form method="post" action="/courses/delete" onsubmit="return confirm('Delete this course?');">
  <input type="hidden" name="id" value="c_abc123">
  <button type="submit">Delete course</button>
</form>
```

Key idea:

- the course `id` is not editable, so we send it as a hidden input

## Data Integrity: What About Registrations?

Our JSON data store has two collections:

- `courses`
- `registrations` (each registration references a `courseId`)

If we delete a course that has registrations, we have a decision to make:

1. block the delete (recommended for now), or
2. cascade delete the registrations, or
3. allow "orphaned" registrations (not recommended)

For this week, we block the delete if a registration exists for the course and show a message.

Later, as our project grows, we can revisit this policy.

## PRG Redirect

After a successful delete, we redirect back to the course list:

- `Location: /courses?deleted=1` with a `303` status

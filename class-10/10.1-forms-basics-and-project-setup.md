# 10.1 Forms Basics and Project Setup

Chapter 11 is where our PHP projects start feeling like "real" web
applications.

When you build for the web, the browser is a **client** and your PHP code runs
on a **server**. Forms are the most common way a browser sends structured input
to the server.

This week we're going to build a small CRUD (create-read-update-delete) application that manages courses
and student registrations. We'll store data in JSON and use a secure project
layout where only the `public/` folder is web-accessible.

## GET vs POST (Conceptually)

A good mental model:

- **GET** is for retrieving a page or resource.
  - data is usually sent in the URL query string
  - easy to bookmark and share
  - good for filters/search
- **POST** is for sending data that changes state.
  - data is sent in the request body
  - commonly used for create/update/delete actions

We'll use both in this app.

## Anatomy of an HTML Form

An HTML form is built from:

- `method` (usually `get` or `post`)
- `action` (where the request is sent)
- inputs with `name` attributes

Example GET form:

```html
<form method="get" action="/debug/get">
  <input type="text" name="q">
  <button type="submit">Search</button>
</form>
```

Example POST form:

```html
<form method="post" action="/debug/post">
  <input type="text" name="message">
  <button type="submit">Submit</button>
</form>
```

The most important attribute is `name`.

- The browser sends key/value pairs based on the input `name`.
- In PHP, prefer retrieving them with `filter_input()` / `filter_input_array()`
  instead of reading `$_GET` and `$_POST` directly.

## PRG: Post-Redirect-Get (High Level)

As we discussed last week, if a POST request returns an HTML page directly,
refreshing the page can re-submit the POST.

A common pattern is **PRG**:

1. browser submits a POST
2. server processes the POST
3. server redirects to a GET page that shows the result

We will use PRG throughout this CRUD app.

## Project Setup: Secure `public/` Web Root

We start a new project.

As we introduced last week, our key rule:

- Only `public/` is meant to be web-accessible.

Everything else (partials, helper functions, JSON storage) lives above the web
root in `app/`.

## Running the App Locally

From the repository root, start PHP's built-in dev server:

```bash
php -S localhost:8080 -t public public/router.php
```

Then visit:

- `http://localhost:8080/`

## Pages We Add in 10.1

This tutorial includes a few simple pages so we can observe form requests:

- `/debug/get` shows a GET form and dumps `filter_input_array(INPUT_GET, ...)`
- `/debug/post` shows a POST form and uses a 303 redirect (PRG)
- `/debug/post-result` shows the result of the redirect

These are not the final CRUD screens. They are here to make the request/response
process obvious before we start building course and registration interfaces.

## What to Observe in DevTools

Open DevTools -> Network and compare:

- the GET request to `/debug/get` (query string parameters)
- the POST request to `/debug/post` (request body)
- the redirect (303) and the follow-up GET request to `/debug/post-result`
